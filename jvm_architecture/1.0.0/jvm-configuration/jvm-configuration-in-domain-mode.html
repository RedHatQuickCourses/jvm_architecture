JVM Configuration in Domain Mode

This section delves into the specifics of configuring Java Virtual Machine (JVM) parameters within a managed domain environment, such as JBoss EAP or WildFly. Unlike standalone mode where configuration applies to a single server instance, domain mode introduces centralized management across multiple server instances, often grouped into server groups. Understanding this architectural difference is key to effectively managing JVM settings in a clustered or distributed application environment.

Introduction to JVM Configuration in Domain Mode

In a managed domain, multiple server instances can be controlled from a single point, the Domain Controller. These server instances are organized into server groups, and each server group can host various application servers (called servers or server instances). JVM configurations in domain mode are typically applied at the server group level, ensuring consistency for all servers belonging to that group. This approach simplifies management and promotes uniformity across your application deployments.

The primary goal of configuring JVM parameters in a domain is to optimize the performance and stability of your Java applications running on the servers within that domain. This often involves adjusting memory allocation (heap, Metaspace), selecting appropriate garbage collectors, and setting other JVM flags.

Understanding Domain Mode for Configuration

Before diving into configuration specifics, it’s essential to briefly recall the core components of a managed domain:

  • Domain Controller (DC): The central point of management for the entire domain. It stores the domain configuration (domain.xml).

  • Host Controller (HC): Runs on each physical or virtual machine within the domain. It manages the server instances on its host and communicates with the Domain Controller. It stores host-specific configuration (host.xml).

  • Server Group: A logical grouping of server instances that share a common configuration profile and JVM settings.

  • Server Instance: An individual application server process (e.g., JBoss EAP server) that belongs to a server group.

When you configure JVM settings in domain mode, you are essentially modifying the profile or server group definition within the domain.xml file, which is then distributed and applied by the Host Controllers to the relevant server instances.

Key Configuration Concepts in Domain Mode

Configuring JVMs in a domain environment involves understanding how settings are inherited and applied:

  • Profiles: Domain mode uses profiles (e.g., default, full, full-ha) to define subsystems and configurations. Server groups are associated with a specific profile. While JVM settings aren’t directly part of a profile definition in the same way subsystems are, they are often linked to the server group that uses a profile.

  • Server Groups: This is the primary abstraction for JVM configuration. Each server group can have its own JVM settings defined. All servers within a server group will inherit these settings.

  • JVM Elements: Within the server group definition, a <jvm> element is used to specify various JVM settings, including memory parameters, garbage collector options, and system properties.

The most common JVM parameters to configure are related to memory:

  • Initial Heap Size (-Xms): The initial amount of memory allocated to the JVM heap.

  • Maximum Heap Size (-Xmx): The maximum amount of memory the JVM heap can use.

  • Maximum Metaspace Size (-XX:MaxMetaspaceSize): The maximum size for Metaspace, where class metadata is stored (replaces PermGen in Java 8+).

Setting -Xms and -Xmx to the same value can help reduce garbage collection pauses by preventing the heap from resizing. However, this also means the JVM will immediately claim the maximum allocated memory, which might not be efficient for environments with many small JVMs.

Methods for JVM Configuration in Domain Mode

There are two primary ways to configure JVM settings in a JBoss EAP/WildFly domain:

  1. Using jboss-cli.sh (Recommended): The command-line interface is the most robust and recommended method. It ensures proper validation, syntax, and propagates changes across the domain safely.

  2. Directly editing domain.xml: While possible, direct editing is generally discouraged, especially in production environments, as it bypasses validation and can lead to errors if not done carefully. Changes require reloading or restarting the domain.

1. Using jboss-cli.sh

The jboss-cli.sh tool allows you to interact with the Domain Controller and apply configuration changes. For JVM settings, you typically target a specific server group.

The general approach involves: . Connecting to the Domain Controller. . Navigating to the /server-group=YOUR_SERVER_GROUP_NAME/jvm=YOUR_JVM_NAME path. . Using add, write-attribute, or remove operations to manage JVM settings.

The jvm resource within a server group can be named arbitrarily (e.g., default, my-jvm, app-jvm). If no JVM is explicitly defined for a server group, it might inherit a default or use minimal settings.
Example: Adding a new JVM configuration to a server group

To create a JVM configuration named my-jvm for a server group called main-server-group, you would use commands similar to these:

# Connect to the Domain Controller
/path/to/jboss-eap/bin/jboss-cli.sh --connect

# Add a JVM configuration named 'my-jvm' to the 'main-server-group'
# (This creates the JVM configuration element)
/server-group=main-server-group/jvm=my-jvm:add()

# Set initial heap size (Xms) to 512m
/server-group=main-server-group/jvm=my-jvm:write-attribute(name=heap-init, value=512m)

# Set maximum heap size (Xmx) to 2048m
/server-group=main-server-group/jvm=my-jvm:write-attribute(name=heap-max, value=2048m)

# Set maximum Metaspace size to 512m
# Note: Other JVM options are typically added via the 'jvm-options' list.
# For MaxMetaspaceSize, it's a common practice to include it in jvm-options.
/server-group=main-server-group/jvm=my-jvm:write-attribute(name=jvm-options, value=["-XX:MaxMetaspaceSize=512m"])

# To add multiple jvm-options, provide a comma-separated list
# Example: Adding a garbage collector and another option
/server-group=main-server-group/jvm=my-jvm:write-attribute(name=jvm-options, value=["-XX:MaxMetaspaceSize=512m", "-XX:+UseG1GC", "-Dmy.custom.property=value"])

# To read the current configuration for verification
/server-group=main-server-group/jvm=my-jvm:read-resource

# Reload the server group for changes to take effect
/server-group=main-server-group:reload-servers()
Example: Modifying an existing JVM configuration

If a JVM configuration already exists (e.g., named default for main-server-group), you can modify its attributes directly:

# Connect to the Domain Controller
/path/to/jboss-eap/bin/jboss-cli.sh --connect

# Read current attributes to see what's set
/server-group=main-server-group/jvm=default:read-resource

# Modify the max heap size
/server-group=main-server-group/jvm=default:write-attribute(name=heap-max, value=4096m)

# Modify JVM options (this *replaces* the existing list, so include all desired options)
/server-group=main-server-group/jvm=default:write-attribute(name=jvm-options, value=["-XX:MaxMetaspaceSize=768m", "-XX:+UseParallelGC"])

# Reload servers in the group
/server-group=main-server-group:reload-servers()

2. Directly Editing domain.xml

While not recommended for production, understanding the domain.xml structure can be helpful for advanced troubleshooting or specific use cases.

The relevant section in domain.xml will be within the <server-groups> element:

<server-groups>
    <server-group name="main-server-group" profile="full">
        <jvm name="my-jvm"> (1)
            <heap size="512m" max-size="2048m"/> (2)
            <jvm-options> (3)
                <option value="-XX:MaxMetaspaceSize=512m"/>
                <option value="-XX:+UseG1GC"/>
            </jvm-options>
        </jvm>
        <socket-binding-group ref="standard-sockets"/>
    </server-group>
</server-groups>
1 Defines a JVM configuration named my-jvm for main-server-group.
2 Sets the initial (size) and maximum (max-size) heap.
3 Lists additional JVM options.

Changes made directly to domain.xml require the Domain Controller and potentially the Host Controllers and server instances to be reloaded or restarted for the changes to take effect.

Real-world Examples and Best Practices

Consider the following scenarios and best practices when configuring JVMs in a domain:

  • Homogeneous Server Groups: For optimal stability and simplified management, create server groups where all servers have similar resource requirements. This allows a single JVM configuration to be applied consistently.

  • Dedicated Memory: Allocate sufficient memory for each server instance. A common mistake is to over-provision the number of servers on a physical host without considering the cumulative memory requirements, leading to out-of-memory errors or excessive swapping.

  • Garbage Collector Selection:

  • G1GC (-XX:+UseG1GC): Often a good choice for multi-processor machines with large heaps (4GB or more) that require predictable pause times.

  • ParallelGC (-XX:+UseParallelGC): Good for throughput-oriented applications where short garbage collection pauses are less critical.

  • CMS (-XX:+UseConcMarkSweepGC): Deprecated in newer Java versions, but historically used for low-latency applications. Prefer G1GC or ZGC/ShenandoahGC (if available and licensed).

  • Metaspace Sizing: Monitor Metaspace usage. If java.lang.OutOfMemoryError: Metaspace errors occur, increase -XX:MaxMetaspaceSize. Start with a reasonable default (e.g., 256m or 512m) and adjust based on application needs.

  • Troubleshooting:

  • Enable garbage collection logging (-Xlog:gc*:/path/to/gc.log:time,level,tags).

  • Use JConsole, VisualVM, or JMC (Java Mission Control) to monitor JVM health and memory usage in real-time.

  • Analyze heap dumps (-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/to/dumps) to identify memory leaks.

Hands-on Lab: Configuring JVM Memory for a Server Group

In this lab, you will configure the JVM memory settings for a server group in a JBoss EAP/WildFly managed domain using the jboss-cli.sh tool.

Lab Objective

To successfully modify the initial and maximum heap size, and add a Metaspace size limit for a specific server group within a JBoss EAP/WildFly domain.

Prerequisites

  • A running JBoss EAP or WildFly managed domain setup. This includes:

  • A Domain Controller (DC) instance.

  • At least one Host Controller (HC) instance registered with the DC.

  • At least one server group (e.g., main-server-group or other-server-group) with active server instances.

  • Access to the jboss-cli.sh utility.

Step-by-step Instructions

  1. Start your JBoss EAP/WildFly Domain Controller and Host Controller(s). If they are not already running, navigate to your JBoss EAP/WildFly installation directory and start them: [source,bash] ---- # On the Domain Controller host ./bin/domain.sh

    # On a Host Controller host
./bin/host.sh
----

  2. Connect to the Domain Controller using jboss-cli.sh. Open a new terminal and navigate to the bin directory of your JBoss EAP/WildFly installation. Then, connect to the CLI: [source,bash] ---- ./jboss-cli.sh --connect ---- You should see a prompt like [domain@localhost:9990 /].

  3. Identify an existing server group. List the available server groups to choose one for configuration. For this lab, we will assume a server group named main-server-group exists. [source,bash] ---- /server-group:read-resource ---- Look for a server group like main-server-group or other-server-group.

  4. Read the current JVM configuration for your chosen server group. Before making changes, inspect the current JVM settings for the main-server-group. We’ll assume a JVM configuration named default exists. If not, you might need to add one in the next step. [source,bash] ---- /server-group=main-server-group/jvm=default:read-resource ---- If this command fails with an error like WFLYCTL0216: Management resource …​ not found, it means no default JVM configuration exists. You’ll need to create it.

  5. Configure JVM memory parameters. We will set the initial heap to 512MB (-Xms512m), maximum heap to 2GB (-Xmx2g), and maximum Metaspace size to 512MB (-XX:MaxMetaspaceSize=512m).

    • If no default JVM configuration exists: Create the default JVM element and set parameters. [source,bash] ---- /server-group=main-server-group/jvm=default:add() /server-group=main-server-group/jvm=default:write-attribute(name=heap-init, value=512m) /server-group=main-server-group/jvm=default:write-attribute(name=heap-max, value=2g) /server-group=main-server-group/jvm=default:write-attribute(name=jvm-options, value=["-XX:MaxMetaspaceSize=512m"]) ----

    • If a default JVM configuration already exists: Modify the existing attributes. Remember that jvm-options will replace the entire list, so ensure you include all desired options. [source,bash] ---- /server-group=main-server-group/jvm=default:write-attribute(name=heap-init, value=512m) /server-group=main-server-group/jvm=default:write-attribute(name=heap-max, value=2g) /server-group=main-server-group/jvm=default:write-attribute(name=jvm-options, value=["-XX:MaxMetaspaceSize=512m"]) ----

  6. Verify the changes. Read the resource again to confirm your new settings. [source,bash] ---- /server-group=main-server-group/jvm=default:read-resource(include-runtime=true) ---- You should see heap-init, heap-max, and jvm-options reflecting your changes. The include-runtime=true will show current settings for running servers, which won’t reflect the new values until reloaded.

  7. Reload the server group to apply changes. For the changes to take effect on the running server instances within the main-server-group, you must reload them. [source,bash] ---- /server-group=main-server-group:reload-servers() ---- Confirm the operation by typing yes when prompted.

  8. Validate the configuration on a running server. After reloading, connect to one of the server instances belonging to main-server-group (e.g., server-one) and check its JVM arguments. [source,bash] ---- /host=master/server=server-one/jvm=default:read-resource(include-runtime=true) ---- Look at the system-properties or vm-arguments (depending on JBoss EAP/WildFly version and specific output structure) to confirm -Xms512m, -Xmx2g, and -XX:MaxMetaspaceSize=512m are present. You can also view the server logs for startup messages indicating JVM options.

Expected Outcome

After completing the lab, the JBoss EAP/WildFly server instances within the main-server-group will be configured to start with an initial JVM heap of 512MB, a maximum heap of 2GB, and a maximum Metaspace size of 512MB. You should be able to verify these settings using the jboss-cli.sh.

Validation Steps

  1. After reload-servers(), run /server-group=main-server-group/jvm=default:read-resource again and ensure heap-init, heap-max, and jvm-options show the configured values.

  2. Check the server logs (server.log) for any server instance in the main-server-group. During startup, the server often logs the JVM arguments it is using. Search for -Xms, -Xmx, and MaxMetaspaceSize in these logs.

Common Errors and Troubleshooting

  • WFLYCTL0216: Management resource […​] not found: This error indicates that the specific jvm=default resource does not exist for the main-server-group. You need to add it using the add() operation first, as shown in the instructions.

  • Incorrect syntax in jvm-options: JVM options are case-sensitive and must be specified exactly. A typo (e.g., MaxMetaspace instead of MaxMetaspaceSize) will lead to the JVM failing to start or ignoring the option. Always verify with read-resource.

  • Servers failing to restart/reload: If the servers fail to reload or come up, check the server.log for the specific server instance on the Host Controller machine. Look for java.lang.OutOfMemoryError messages or Invalid initial heap size errors, which might indicate incorrect memory values (e.g., -Xms greater than -Xmx, or values too large for the available physical memory).

  • Changes not taking effect: Ensure you have executed the reload-servers() command for the respective server group. Configuration changes are not active until the servers are reloaded or restarted.

  • Operation failed: If a CLI operation fails, read the error message carefully. It often provides clues about invalid attributes, values, or incorrect paths.
