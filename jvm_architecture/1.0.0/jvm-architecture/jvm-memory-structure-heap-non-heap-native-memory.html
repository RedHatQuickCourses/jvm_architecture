JVM Memory Structure (Heap, Non-Heap, Native Memory)

This section delves into the fundamental memory architecture of the Java Virtual Machine (JVM), exploring how it allocates and manages memory from the underlying operating system to execute Java applications. Understanding these memory areas is crucial for performance tuning, troubleshooting memory-related issues, and optimizing resource utilization.

Overview of JVM Memory Areas

The JVM manages several distinct memory areas that are used for various purposes during the execution of a Java application. These areas are primarily categorized into Heap memory, Non-Heap memory, and the broader concept of Native memory. While Heap and Non-Heap are directly managed by the JVM’s garbage collector or internal mechanisms, Native memory refers to the total footprint the JVM process consumes from the operating system, which includes the Heap and Non-Heap, along with other OS-level allocations like thread stacks and direct byte buffers.

Heap Memory

The Heap is the most critical and typically the largest memory area managed by the JVM. It is the runtime data area from which memory for all Java class instances (objects) and arrays is allocated.

Purpose and Characteristics

  • Object Storage: All objects created by a Java application (e.g., new MyClass(), new int[10]) reside in the Heap.

  • Shared Resource: The Heap is shared among all threads of a running Java application.

  • Garbage Collection (GC): Memory in the Heap is automatically managed by the JVM’s garbage collector. When objects are no longer referenced by the application, the GC reclaims their memory, making it available for new objects.

  • Dynamic Size: The Heap is created when the JVM starts and its size can dynamically increase or decrease during application execution, within predefined limits. These limits are configured using JVM arguments.

Heap Memory Configuration

The size of the Heap memory is typically configured using two main JVM arguments:

  • -Xms<size>: Specifies the initial (minimum) Heap size. The JVM starts with this amount of memory allocated to the Heap.

  • -Xmx<size>: Specifies the maximum Heap size. The Heap will not grow beyond this limit.

If the application attempts to allocate objects beyond the maximum Heap size, an OutOfMemoryError: Java heap space will be thrown, causing the application to fail.

Real-world Example: Web Server Application

Consider a web server application. Each incoming user request might create several objects: a HttpRequest object, HttpResponse object, session data objects, database connection objects, and objects for processing business logic. All these objects are allocated in the Heap. If the server experiences a sudden surge in traffic, it will create many more objects, requiring the Heap to expand up to its -Xmx limit. If the limit is too low, the application will crash.

Non-Heap Memory

Non-Heap memory, also known as Native memory in some contexts from the perspective of Java objects not residing there, is distinct from the Heap. It stores metadata, JVM internal structures, and compiled code, rather than application data objects.

Components of Non-Heap Memory

The Non-Heap memory area comprises several key sub-components:

Metaspace

  • Purpose: Stores metadata about loaded classes. This includes class definitions, method data, field data, and runtime constant pools. In older JVM versions (Java 7 and earlier), this was known as PermGen (Permanent Generation).

  • Characteristics: Metaspace can automatically expand its size up to the available native memory of the host system, by default. However, its maximum size can be controlled using the -XX:MaxMetaspaceSize=<size> JVM argument. If not explicitly limited, a memory leak in class loading can exhaust the system’s native memory.

  • Impact: Excessive class loading or class loader leaks can lead to OutOfMemoryError: Metaspace.

Code Cache

  • Purpose: Stores the native code generated by the JVM’s Just-In-Time (JIT) compiler. The JIT compiler optimizes frequently executed Java bytecode into native machine code for improved performance.

  • Characteristics: The size of the Code Cache can be configured using -XX:ReservedCodeCacheSize=<size>.

  • Impact: If the Code Cache becomes full, the JIT compiler will stop compiling new code, potentially leading to performance degradation as the JVM reverts to interpreting bytecode.

JVM Internal Structures

  • Purpose: This area houses various internal data structures used by the JVM itself. This includes:

  • JVM’s own code and data.

  • Profiler agent data.

  • Just-In-Time (JIT) compiler internal data.

  • Garbage Collector data structures.

  • Symbol tables, etc.

  • Characteristics: This memory is managed directly by the JVM and its size is influenced by the JVM version and configuration.

Thread Stacks

  • Purpose: Each Java thread has its own private stack memory. This stack stores method call frames, local variables, and partial results.

  • Characteristics: The size of each thread’s stack can be configured using -Xss<size>. If a program has deep recursion or many method calls, it might run out of stack space, resulting in a StackOverflowError.

  • Note: While distinct from Heap and other Non-Heap areas, thread stacks are part of the overall native memory consumed by the JVM process.

Native Memory (Operating System Memory)

Native memory refers to the total memory allocated by the operating system for the entire JVM process. This encompasses all the memory used by the JVM, including the Heap, Non-Heap components, and other allocations that are not directly managed by the Java runtime but are part of the JVM process’s footprint.

Relationship to Heap and Non-Heap

  • The Heap and Non-Heap (Metaspace, Code Cache, etc.) are memory regions within the JVM process that obtain their memory from the overall native memory allocated by the OS to that process.

  • Beyond the JVM-managed areas, native memory also includes:

  • Direct Byte Buffers: Memory allocated outside the Java Heap for direct I/O operations (e.g., using java.nio.ByteBuffer.allocateDirect()).

  • JNI (Java Native Interface) Memory: Memory allocated by native libraries loaded via JNI calls.

  • OS/JVM Overheads: Memory used by the operating system for process management, JVM internal code, and other system resources.

Real-world Scenario: Native Memory Leaks

A common issue is a native memory leak, which can occur if an application uses direct byte buffers or JNI libraries that do not properly release native memory. Even if your Java Heap is perfectly managed by the GC, the overall JVM process can consume more and more OS memory, eventually leading to the OS killing the process or system instability. This can manifest as the JVM process’s memory footprint (as seen by top or ps) growing even though the Java Heap (jstat) remains stable.

Hands-on Lab: Observing JVM Memory Usage

In this lab, you will start a simple Java application with specific Heap memory settings and then observe its memory usage from the operating system perspective.

Objective

  • Understand how to configure JVM Heap memory parameters (-Xms, -Xmx).

  • Observe the difference between JVM-reported Heap usage and the overall process memory footprint from the OS.

Prerequisites

  • A Linux environment (e.g., CentOS, RHEL).

  • JDK installed (e.g., OpenJDK 11 or higher). If not, refer to the "Installing JDK using Subscription Manager" lab.

  • Basic familiarity with command-line tools (java, jps, top, ps).

Step-by-Step Instructions

Step 1: Create a Sample Java Application

We will create a simple Java application that continuously allocates objects to gradually fill the Heap.

  1. Create a file named MemoryEater.java with the following content:

    import java.util.ArrayList;
import java.util.List;

public class MemoryEater {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("MemoryEater application started.");
        List<byte[]> list = new ArrayList<>();
        int mb = 1024 * 1024;
        long totalMemoryAllocated = 0;

        try {
            while (true) {
                byte[] data = new byte[mb]; // Allocate 1 MB
                list.add(data);
                totalMemoryAllocated += mb;
                System.out.println("Allocated " + (totalMemoryAllocated / mb) + " MB. Current list size: " + list.size());
                Thread.sleep(100); // Small pause to allow observation
            }
        } catch (OutOfMemoryError e) {
            System.err.println("Caught OutOfMemoryError: " + e.getMessage());
            System.err.println("Total memory allocated before OOM: " + (totalMemoryAllocated / mb) + " MB");
            Thread.sleep(60000); // Keep alive for a minute to observe
        } finally {
            System.out.println("MemoryEater application exiting.");
        }
    }
}

  2. Compile the Java application:

    javac MemoryEater.java
Step 2: Run the Application with Specific Heap Settings

We will run the MemoryEater application with an initial Heap size of 64MB and a maximum Heap size of 256MB.

  1. Open two terminal windows.

  2. In the first terminal, start the MemoryEater application:

    java -Xms64m -Xmx256m MemoryEater &

    The & puts the process in the background, allowing you to get your prompt back. Note down the PID (Process ID) that is displayed (e.g., [1] 12345). If it’s not displayed, you can find it using jps in the next step.

Step 3: Monitor JVM and OS Memory

Now, observe how the JVM allocates and consumes memory.

  1. In the second terminal, find the PID of your MemoryEater application using jps:

    jps -l

    Identify the PID corresponding to MemoryEater. Let’s assume it’s 12345.

  2. Monitor the Java Heap usage using jstat:

    jstat -gc 12345 1s

    This command will print garbage collection statistics every 1 second. * Observe the S0C, S1C, EC, OC, MC, CCSC columns (Capacity of Survivor spaces, Eden, Old, Metaspace, Compressed Class Space). * Notice OU (Old Used) and EU (Eden Used) growing as the application allocates objects. * The YGC (Young GC count) and FGC (Full GC count) will increase as garbage collection occurs. * The sum of S0C + S1C + EC + OC should roughly match your -Xmx setting when fully utilized.

    +

    jstat provides a deep view into Java Heap and GC behavior. OU and EU represent the actual amount of Java objects stored in the Heap at that moment.

  3. Monitor the overall process memory usage using top or ps:

    top -p 12345

    Or, for a snapshot:

    ps aux | grep MemoryEater

    • In top, observe the RES (Resident Set Size) and VIRT (Virtual Memory Size) columns for your process.

    • RES indicates the amount of physical RAM the process is currently using.

    • Notice that RES will be higher than the sum of used Heap (OU + EU) from jstat. This difference accounts for Non-Heap memory (Metaspace, Code Cache, thread stacks, JVM internal structures, etc.).

      RES from top represents the native memory footprint of the JVM process.
Step 4: Observe OutOfMemoryError

Let the MemoryEater application continue running. It will eventually hit the -Xmx256m limit.

  1. In the first terminal (where MemoryEater is running), observe the output. You will see it printing "Allocated X MB" messages.

  2. Eventually, it will print "Caught OutOfMemoryError: Java heap space" and then pause for a minute.

  3. While it’s paused, observe jstat and top again. Notice that even after the OutOfMemoryError, the process still consumes significant memory, as the JVM itself and the collected objects still occupy space until the process fully exits.

Step 5: Clean Up

  1. After observing the OutOfMemoryError and the subsequent pause, kill the MemoryEater process.

    kill 12345 # Replace 12345 with your actual PID

  2. Verify it’s gone:

    jps

Expected Outcome

  • The MemoryEater application starts and continuously allocates memory.

  • jstat shows the Java Heap usage (OU, EU) increasing, followed by occasional GC cycles.

  • top shows the RES memory usage of the java process increasing as the Heap expands and other JVM memory areas are utilized.

  • The application eventually throws an OutOfMemoryError: Java heap space when it exceeds the -Xmx limit.

  • The RES memory reported by top will consistently be higher than the used Heap memory reported by jstat, demonstrating the existence of Non-Heap and other native memory components.

Validation Steps

  • Confirm the OutOfMemoryError message in the MemoryEater terminal.

  • Compare the maximum OU + EU reported by jstat (should be close to 256MB) with the RES value reported by top just before the OOM. The RES value will be higher.

Common Errors and Troubleshooting

  • Error: Could not find or load main class MemoryEater: Ensure you compiled the MemoryEater.java file correctly (javac MemoryEater.java) and are running the java command from the same directory where MemoryEater.class resides.

  • java.lang.OutOfMemoryError: Java heap space (Unexpectedly early): You might have used smaller -Xmx values. Increase -Xmx to allow more memory allocation.

  • jps or jstat command not found: Ensure your JDK is properly installed and the bin directory of your JDK is in your system’s PATH environment variable.

  • Process doesn’t show in top: Double-check the PID. Make sure the Java process is still running. Use ps -ef | grep java to see all Java processes.
